SafeAI.sg

SafeAI.sg is Singapore's first industry-led Centre of Excellence for practical AI governance. It helps organisations deploy AI with the right level of rigour: proportionate to risk, free to access and built by practitioners for practitioners.

It is not a regulator, it does not certify anyone and it does not endorse products.

The problem it addresses is a common one. Many organisations over-govern low-risk AI tools, which stifles useful work, while under-governing high-risk ones, which creates avoidable harm. SafeAI.sg's answer is to match the amount of governance to the amount of risk.

UARS: the Universal AI Use-Case Risk Score

UARS stands for Universal AI Use-Case Risk Score. It is SafeAI.sg's proposed method for scoring how risky an AI use case is, so an organisation can decide how much governance it needs. You score the use case on five dimensions, combine them into one number, and that number places the use case in one of three tiers. SafeAI.sg offers a free, self-service toolkit for doing this in about 30 minutes.

A higher total means more risk and therefore more governance. It is a proposed illustrative framework, not a standard.

Why agents need runtime governance, not only build-time governance

In a traditional stage-gated lifecycle, governance is concentrated at build time: requirements, design review, testing and a sign-off, after which the software is assumed to behave as approved. Agents break that assumption, because their behaviour is decided while they run. This section contrasts the two models so the rest of the page makes sense. Why the stage-gated assumptions break for agents

Behaviour is non-deterministic and path-dependent

The same request can take different routes through different tools and produce different results. Research on runtime governance makes the point that this behaviour cannot be fully governed at design time.1

Inputs are open-ended and can be hostile

Agents read documents, email and tool results. Any of it can carry instructions meant to redirect them. OWASP's agentic risk list puts goal hijack and tool misuse at the top.4

Autonomy multiplies the effect of a mistake

An agent that can call tools turns a wrong judgement into an action, and one action can trigger the next.

Behaviour drifts without any code change

A model update, a new document in the knowledge base or a changed tool response alters behaviour while the signed-off artefact stays the same.

Speed and scale outrun human review

Agents act faster than periodic review can follow, so controls that depend on a person reading a report after the fact arrive too late.

One rule, two worlds

The same policy, governed in each model. Settlements above the handler's limit need a supervisor decision.

Build-time governance

  1. A requirement is written: settlements above a limit need a supervisor.
  2. The design is reviewed and the rule is coded as a check in the claims application.
  3. Twelve test cases are signed off in user acceptance testing.
  4. The system is released. Governance moves to a yearly audit.
  5. In production, a path nobody anticipated, such as a different tool that also pays a claim, is not checked. Nobody sees it until the audit.

Run-time governance

  1. The rule is a policy in the policy engine, with an owner, a version and tests.
  2. The agent proposes each settlement as a structured intent before anything runs.
  3. The engine decides allow, deny or escalate for that intent, whichever tool or path the agent used. A supervisor approves anything above the limit.
  4. An injected invoice asks for the full amount. The engine denies it, the alert fires and the attempt becomes a new eval case.
  5. The rule changes next month. It is updated once in the engine, tested, and applies to every agent at once.

What to keep and what to add

Keep from the lifecycle you know

  • Requirements and specification. The policy catalogue and acceptance evals are the new requirements document.
  • Threat modelling and design review. They still come first, and they now feed the test scenarios and the runtime rules.
  • Independent testing and release gates. They become evals and an evidence pack, enforced by admission control.
  • Change control and separation of duties. They apply to prompts, models, tools and policy packs as well as code.
  • Documentation and ownership. They become policy as code, runbooks and named owners.

Add for agents

  • A decision point that evaluates each consequential intent before it runs.
  • Scoped, short-lived credentials and parameter limits at the tool.
  • Trajectory monitoring, circuit breakers and scoped kill switches.
  • Tamper-evident decision logs and runtime probes that keep proving the controls work.
  • Expiring evidence, so a pack proves today's agent and not last quarter's.

The short version: governance moves from a gate to a loop. The gate still exists, and the loop keeps running for as long as the agent does.

A fair reading

  • Royce's 1970 paper is the source of the stage-gated picture, yet it warned that a single pass through sequential stages is risky and recommended iteration and feedback.2 Here, waterfall means the front-loaded, gate-centred governance pattern, not a claim about how every team works.
  • Modern DevOps and CI/CD already add continuous controls to delivery, such as automated tests, staged rollout and monitoring. Runtime governance extends the same thinking from deploying software safely to governing behaviour safely.
  • This is not a replacement for build-time governance. It is a superset: the gates stay, and the governance continues while the agent runs. Frameworks such as IMDA's for agentic AI also pair assessing and bounding risks upfront with technical controls and monitoring.3

Doer-checker: independent checking inside the loop

The doer-checker model adds a second, independent mind to the loop. A doer agent, powered by one model, proposes the action. A checker agent, powered by a model from a different provider and equipped with different skills, assesses the proposal independently, without being anchored by the doer's reasoning. It is the machine version of two long-standing controls: the maker-checker or four-eyes principle in finance, and design diversity in safety-critical engineering, where independently built components are used so that one fault does not defeat both.

It also matches the separation in the Agent Control Standard, where a guardian agent inspects what an agent is about to do and returns a verdict before it happens.5 Here the checker supplies a reasoned second opinion, and the policy engine remains the decision point.

Rules that keep the checker independent

  1. Use a different provider and model family for the checker. Same-family judges favour their own outputs and their family's, so a same-family checker is the weakest option.1,2
  2. Give the checker different skills, not just a different model. Diversity of how it reasons matters more than the number of checkers.4
  3. Blind the checker. It receives the structured intent and the evidence, never the doer's reasoning, summary or confidence.
  4. Frame the task neutrally: assess the proposal, do not approve it, and assume it may be wrong.
  5. Let the checker verify evidence itself through read-only access to systems of record, instead of trusting the doer's account of the facts.
  6. Keep the checker's rubric hidden from the doer, and do not optimise the doer against the checker's verdicts, or the doer will learn to please it.
  7. Separate the infrastructure: own keys, budgets, rate limits, logs and identity for each model.
  8. Pin and change-control both model versions. A silent update to either one changes the pair's behaviour.
  9. Make the checker advisory: it can only tighten an outcome, and the policy engine and the people remain the authority.

Why the research shapes the design

What the research shows
What it means for the design
Frontier LLM judges favour their own outputs, and the bias tracks their ability to recognise them.1
Do not let a model check its own work, or a sibling model. Use a different provider.
Even with objective, programmatically verifiable rubrics, judges can be up to 50 percent more likely to wrongly mark a failing output as passing when it came from themselves or their family.2
A same-family checker can pass bad proposals while looking rigorous. The cross-provider rule is a requirement, not a preference.
Model errors are substantially correlated across providers: on one dataset, models agreed 60 percent of the time when both erred, and larger, more accurate models were highly correlated even across distinct providers.3
Different providers are necessary but not sufficient. Add skill diversity, blinding and a deterministic backstop, and measure the pair's error correlation yourself.
In a panel of nine judges from seven families, effective independence plateaued at roughly 2.3 to 3.1 votes, and adding judges beyond five gave negligible benefit.4
A bigger panel of similar models is not the answer. Diversify the reasoning, and keep humans for disagreements.

The conclusion is balanced. Using a different provider is a necessary step, because same-family checking is demonstrably biased. It is not enough on its own, because even different providers share errors. That is why the design adds different skills, blinded inputs, independent evidence and a deterministic backstop.

The governing rule: the checker can only make an outcome stricter. It cannot override a deterministic deny and it cannot turn an escalation into an allow. This keeps the final authority with the policy engine and with people, and stops a persuasive but wrong checker from loosening a control.

What to measure

  • Detection rate: the share of seeded faults and known-bad proposals the checker catches.
  • False alarm rate: how often it disagrees with a correct proposal, which sets the human review load.
  • Disagreement rate and its trend, by use case and by tier.
  • Error correlation: the share of golden-set cases where both the doer and the checker are wrong.
  • Human override rate on disagreements, in both directions.
  • Added latency and cost per checked intent.
  • Drift after any model version change on either side.
  • The checker's own red-team results, including injection aimed at the checker.

Six enforcement points, one decision point

The policy engine decides. These six places apply the decision. Each one stops a different class of problem, and each has a blind spot. The blind spot matters as much as the strength, because it tells you which other control has to sit beside it. Read each block as: what this point does, what it cannot do alone, and how the gap gets covered.

Channel and identity

What it can enforce

Who is calling, with which rights, at which tier.

What it cannot catch alone

What the agent does once it has started.

Why the gap exists

Identity answers who is acting. It does not answer whether what they are doing is right. Once a legitimate person starts a legitimate agent with valid credentials, every identity check has already passed, and nothing in identity looks at the content the agent reads or the steps it takes afterwards.

How it slips through

A claims handler legitimately starts the settlement assistant. A customer-uploaded invoice carries hidden instructions. The handler, the agent and the credentials are all genuine, so every identity check passes, yet the agent proposes a payment above the policy cover.

What covers it

The tool router and policy engine decide each intent before it runs. Guardrails screen what the agent reads. Observability watches the run as it unfolds.

Why it matters

Strong login and least privilege only cap the damage at the caller's own rights, and those can be large for a finance controller or a senior handler. Teams that lean on identity alone end up with a well-guarded front door and nobody watching what happens inside.

How to test it

Run an authorised user with a poisoned input and confirm a later control stops the action. Check that the caller's rights are a ceiling for the agent, not a starting point.

Harness

What it can enforce

Screening of inputs and outputs, step and time limits, pauses for a person.

What it cannot catch alone

A determined attack that passes probabilistic checks, or actions that happen outside the harness.

Why the gap exists

Guardrails are probabilistic. They catch common patterns and miss novel ones, and attackers can keep rephrasing until something passes. Limits and approval pauses also only apply to calls that actually go through the harness. An agent, script or integration that reaches a tool another way has none of these controls.

How it slips through

An injected instruction is split across two documents so that each half looks harmless to the input screen. Separately, an engineer's script calls the settlement API directly, so no guardrail, step limit or approval ever applies.

What covers it

Deterministic controls outside the prompt, such as policy decisions and scoped credentials at the tool layer. A rule that tools accept calls only from the harness. An inventory that finds unregistered agents, which is the AI-SPM control in the Tier 3 profile.

Why it matters

Guardrails lower the volume of problems but cannot be the last line of defence. If something can act without passing through the harness, then for that action none of the harness controls exist.

How to test it

Red-team with paraphrased and multi-step injections. Try to reach each tool without going through the harness. Compare the inventory with what is actually running to find shadow agents.

Tool router and tools

What it can enforce

Deny-by-default tool access, parameter limits, scoped credentials, intent decisions.

What it cannot catch alone

Harmful use of an allowed tool inside its limits. That is why approvals and monitoring exist.

Why the gap exists

Router rules are written in advance about actions and parameters. They can say a refund must be under a limit. They cannot judge whether a permitted action is wise in context. Each call can be safe on its own while the sequence of calls is not.

How it slips through

The refund tool allows up to S$500 per call. A manipulated agent issues sixty refunds of S$490 to related accounts. Every single call passes the parameter limit, and the total is a serious loss.

What covers it

Cumulative and rate limits in the policy engine. Trajectory monitoring across a run. Human approval triggered by patterns, not only by single amounts. Circuit breakers that halt unusual repetition.

Why it matters

Agentic risk lives in sequences. A router that makes each action safe in isolation can create false confidence, so this blind spot tells teams to write cumulative and contextual rules, not only per-call ones.

How to test it

Simulate many small allowed actions and check that cumulative caps and alerts fire. Review which rules look only at one call and which look at the pattern.

Model gateway

What it can enforce

Approved models, budgets, rate limits and, at Tier 3, inline inspection.

What it cannot catch alone

What the agent does with the answer.

Why the gap exists

The gateway sees prompts and responses between the harness and the models. It does not see the tool calls and side effects that follow. A clean, approved, well-formed response can still be wrong, misunderstood or acted on badly, and content inspection judges form and patterns, not whether the plan is sensible.

How it slips through

The model returns a confident but wrong settlement figure. The gateway sees an approved model, a response inside budget and nothing suspicious. If the agent pays that figure, the loss happens downstream of everything the gateway can see.

What covers it

The tool router and policy engine, which check the action itself. Deterministic tools for calculations. Validation of outputs against authoritative data in the semantic layer. Approvals for larger amounts. Evals that include plausible but wrong answers.

Why it matters

The gateway is the single choke point for model calls, so it is easy to over-trust. Model calls are only one of the two doors out of the harness. The other door, the tool layer, is where actions happen.

How to test it

Check that every tool call is validated independently of what the model said. Add golden-set cases where the model gives a plausible wrong answer and confirm the action is still caught.

Semantic layer and data

What it can enforce

Row and column access from the caller's identity, masking, one definition per metric.

What it cannot catch alone

A permitted user asking for something they should not, in a context that makes it harmful.

Why the gap exists

Entitlements answer whether a person may see data. They do not capture the purpose or context of a request, and they cannot see inference or aggregation. Many individually permitted rows can add up to something the person was never meant to assemble.

How it slips through

A handler with access to claims data asks the assistant to pull a neighbour's claim out of curiosity, or to compile and send an export. Each query is within the handler's entitlements, so row-level security allows all of it.

What covers it

Purpose-aware rules in the policy engine. Approvals for sensitive exports. Output screening for personal data. Limits on where tools may send data. Monitoring and audit for unusual access patterns.

Why it matters

Many data incidents involve authorised access used wrongly. Agents make this easier by doing bulk work quickly, so the question moves from can they see it to should this use happen now.

How to test it

Probe for bulk and unusual queries and for exfiltration through outbound tools. Check that purpose is captured and logged, and that outbound destinations are restricted.

Audit and posture

What it can enforce

Nothing in real time by itself. It records, inventories and supports review.

What it cannot catch alone

Harm before it is noticed, so it relies on the other five.

Why the gap exists

Audit trails and posture inventories are detective controls. They tell you what happened and what exists, after the fact. They cannot stop an action, and they only help if the records are complete, the assets are registered, and people actually review and respond.

How it slips through

An incident has an excellent audit trail showing exactly how a wrong payment was made, but the money has already left. Or the logs are complete and the alert has sat unread for two weeks.

What covers it

The five preventive and real-time points. Alert routing and a review rhythm. Tested incident runbooks. Measures such as time from event to alert to human response.

Why it matters

It is tempting to count logging everything as a control. Logging without prevention moves risk to clean-up. It is also where the evidence for a Tier 3 safety case comes from, so its quality decides how credible that case is.

How to test it

Run an incident drill and check the trail answers who, what, when and why without guesswork. Measure time to detect and time to respond.

Why name the blind spot at every point

Every control has a failure mode

Stating it turns defence in depth from an accident into a design. The blind spot tells you what has to sit beside the control.

The strongest-looking point attracts the most trust

A strong login or a central gateway invites reliance. Naming what it cannot see prevents a team from treating one point as the whole answer.

It makes ownership explicit

Each blind spot points to the controls that cover it, so someone is accountable for the gap instead of assuming another team has it.

It becomes a test case

Every blind spot is a red-team scenario and an eval. You can test that the covering control really catches what the first one misses.

It explains why the tiers stack controls

Human checkpoints, trajectory monitoring, circuit breakers and safety cases exist because earlier controls have these gaps. The tier profiles are the blind spots turned into requirements.

It is honest with boards and reviewers

Showing that you know where each control stops is more credible than claiming coverage. It supports the safety case at Tier 3.

Keeping the forms consistent

  1. Keep a policy catalogue. Each policy has an ID, an owner, a plain-language statement, a tier scope and a review date. Every artefact that enforces part of it cites the ID.
  2. Layer the packs: enterprise baseline, then domain, then agent. Lower layers may tighten and never relax. A test asserts this on every change.
  3. Change them together. When a policy changes, every artefact that cites its ID is reviewed in the same change, and the release carries one new version.
  4. Detect drift. A scheduled job compares limits in manifests and tool contracts with the engine's rules and raises an alert when they disagree.
  5. Log the version. Every decision records the rule version and pack versions, so a reviewer can reconstruct which policy was in force at that moment.
  6. Never rely on one form. Use at least one deterministic enforcement and one verifying test for any policy that matters, and use prompts and procedures for what code cannot say.

Five design rules

  1. The same tests, metrics and datasets run before release and during runtime. A check that only exists in the pipeline cannot notice drift.8
  2. Evidence is bound to exact versions. A pack for last month's prompt, model or policy says nothing about today's agent.
  3. The platform enforces the gate. If a team can deploy by skipping a process step, it is a guideline, not a gate.
  4. Evaluators are independent of builders for anything consequential, and fully independent for the highest tier.
  5. Evidence expires. Time and change both trigger re-testing, and a failed runtime check can revoke an agent's standing.

The evidence pack

A pack turns test results into a release decision artefact: current passing evidence, a baseline to judge regressions against, and a record of what was actually checked.9 It should contain:

  • Hashes of the exact artefacts: agent manifest, prompts, model version, tool contracts, policy pack versions.
  • Dataset versions and judge model versions used, plus thresholds and seeds.
  • Per-requirement results with the test IDs behind them, including statistical confidence where tests are probabilistic.
  • A coverage report: requirements covered, requirements marked not applicable with a reason, and requirements only partly covered.
  • Open waivers with owner, compensating control and expiry.
  • Signatures from the required roles, and an expiry date.

Admission control in the agent manifest

The harness checks the pack when an agent is deployed and again at the start of each run. The check is cheap: compare hashes, check the expiry and the status. If the pack is missing, expired or no longer matches, the agent is refused or restricted.

Making evals consistent and auditable

Consistency is what lets an auditor trust a pass. These practices make a result reproducible and defensible.

  1. Pin and record everything: model, prompts, tools, policy packs, datasets, judge model, seeds and thresholds, bound into the evidence pack.
  2. Keep results in an append-only, hash-chained store so an assessor can trust that history was not edited.
  3. Govern datasets: versioned, with provenance, no overlap between training and test data, negative and unanswerable cases, and every incident turned into a case.8
  4. Govern the judge: pin its version, calibrate it against human-labelled samples, recalibrate on a schedule, and prefer deterministic checks for consequential decisions.
  5. Use statistics honestly: repeated runs, confidence intervals and thresholds with margin. Quarantine flaky tests with an expiry date, never silently ignore them.
  6. Define metrics once and reuse them in the pipeline and in production.8
  7. Separate duties. Builders do not approve their own gates. Evaluators are independent for Tier 2 and above. The red team is independent at Tier 3.
  8. Publish coverage honestly: what is tested, what is not applicable and why, and what is only partly covered.
  9. Run a reproducibility drill: an assessor re-runs a past evaluation from its evidence pack and reaches the same result within tolerance.
  10. Version the standards you adopt. Record which AISVS and ACS versions each pack used, and diff the requirements when you upgrade.

Limits and honest caveats

  • Passing evals is evidence, not proof of safety. Tests sample behaviour, and attackers and workloads change.
  • AISVS is large and not every requirement can be automated. Some need human attestation. Counts differ between sources and drafts: the 1.0 release plan cites 514 requirements across 14 chapters plus 30 in a coding appendix, so pin your version and count from it.2
  • The Agent Control Standard is at an early version. Treat it as a design reference and a direction of travel, and confirm what your agent platforms actually expose.6,7
  • OWASP standards are voluntary. A pack proves conformance to the requirements you chose, not certification. SafeAI.sg is also non-certifying.
  • Model-judged evals are probabilistic. Calibrate them and do not rely on them alone for consequential gates.
  • The mappings on this page, including UARS tier to AISVS level, chapter to component, and the example tests, are suggestions for you to adapt. Always read the requirement text in the standard.

Treat the harness as a product and use cases as its customers

An agent is the model plus its harness, and the harness is where most of the engineering effort now goes: context, tools, permissions, memory, recovery and the feedback loops around them.1 That makes it a platform problem. DORA's 2025 research describes AI as an amplifier of what an organisation already does well or badly, and finds that a quality internal platform and working in small batches are among the capabilities that make AI pay off.4 The practical consequences are these.

  • One shared harness, built and run as a product by a platform team, so that governance, identity, policy, evals and observability are written once.
  • Many use case teams that own outcomes and build on the paved road, rather than each rebuilding a runtime.
  • Small teams at the edge depend on strong shared systems at the centre.1 The smaller the cell, the stronger the platform has to be.
  • Authority follows responsibility. The edge decides roadmap, production and spend. The centre owns universal safeguards, approved capabilities and independent review boundaries.1

    Design principles
    Compile and curate, do not accumulate
    Andrej Karpathy's LLM Wiki pattern from April 2026 keeps three layers apart: immutable raw sources, a maintained wiki, and a schema file of conventions, with ingest, query and lint as the operations.3 The idea is that knowledge is compiled once and kept current instead of being rediscovered on every query. Community write-ups present it mainly for personal and small-team use, so an enterprise needs the ownership, review and access controls in this guide on top.
    Capture in the flow of work
    Knowledge-Centered Service treats knowledge as a by-product of solving problems, captured in context, with the principle that reuse is review.4 Build the same loop: when a person or agent searches and finds nothing, that gap becomes a capture prompt. When they use a note and find it wrong, flagging or fixing it is part of the work.
    Domains own, the centre sets standards
    Data mesh offers a proven shape for a large organisation: domain ownership, treating output as a product, a self-serve platform and federated computational governance.5 Domains write and own notes. A central team provides the platform and the schema, and enforces standards by automation, not by meetings.
    Plain text and open formats
    Markdown with a structured header, stored in version control, is portable, diffable, reviewable and survives any tool change. It also keeps the second brain independent of any single vendor.
    Trust belongs to each note
    A note carries its own owner, status, version, review date, sensitivity and sources. Retrieval filters and ranks on these fields. A base is never simply trusted or untrusted as a whole.
    Permissions travel with the knowledge
    Entitlements are metadata on every note and are enforced when the query runs, using the identity of the caller. The system fails closed.
    Humans approve what agents rely on
    Agents may draft, propose and flag. Only a named owner publishes. This write-path rule is the main defence against poisoned guidance.
    Retrieve just in time, in small pieces
    Anthropic's context engineering guidance treats context as a finite resource and favours lightweight identifiers that agents expand on demand, so progressive disclosure replaces loading everything up front.2 Design the base to be navigable that way.
    Retrieval is a product with tests
    Measure retrieval separately from generation, keep a golden question set, and gate every change to the index, chunking, embeddings or models on those tests.

    Retrieval design for the harness
    The context builder needs five properties from every snippet: relevant, small, attributable, current and permitted. Context is a finite resource, and Anthropic's guidance is to find the smallest set of high-signal tokens that gets the job done.2 The pipeline below is built around that.
    1. Understand the request. Combine the task, the caller's identity, the use case's UARS tier and the domain scope, then rewrite or decompose the query where needed.
    2. Filter first. Restrict to approved status, in-date review, the caller's entitlements, sensitivity and jurisdiction. Apply the same filters on the keyword path and the vector path.
    3. Generate candidates. Run hybrid keyword and vector search over contextualised chunks, with a generous candidate pool.
    4. Rerank. Pass the pool to a reranker and keep a small, tuned number of chunks.
    5. Expand through links. Follow supersedes, glossary and related links, prefer the current version and drop superseded notes.
    6. Assemble. Delimit each snippet, label it with note ID, version, status, owner, trust tier and review date, and respect the token budget.
    7. Log. Record the note IDs and versions used into the harness trace for that step.
    What the research supports
    • Contextual retrieval: prepending a short model-generated context of about 50 to 100 tokens to each chunk before embedding and keyword indexing. In Anthropic's published tests the top-20 retrieval failure rate fell from 5.7 percent to 3.7 percent with contextual embeddings, 2.9 percent adding contextual keyword search, and 1.9 percent with reranking. Twenty chunks outperformed ten or five in those tests. Results depend on your corpus, so measure your own.1
    • Compiled wiki first, retrieval second. For core guidance, a short, well-linked set of curated notes with an index note lets an agent navigate by progressive disclosure.2,3 Keep hybrid retrieval for the long tail and for raw sources.
    • Graph retrieval where it earns its cost. GraphRAG extracts entities and relationships with a model, clusters them into communities, and summarises each community. Its global search suits corpus-wide questions and its local search suits entity questions. It is not worth the construction cost if questions are only local.6 Start with the explicit typed links already in your notes before extracting a graph.

    Serving over MCP
    • The 2026-07-28 revision of MCP is stateless: the initialize handshake and session header are gone, each request carries its protocol version and client capabilities, and servers expose a discovery method.10,11 A knowledge gateway can therefore scale like any HTTP service.
    • Capability listings are cacheable under the new revision, and the specification adds an extension model.17 Keep the tool set small, with clearly distinct names and descriptions.
    • Authorization builds on OAuth and OpenID Connect. Earlier revisions added resource indicators and incremental scope consent.10 Issue audience-bound tokens for the gateway, check the audience and scopes on every request, and carry the end user's identity so entitlements are evaluated for the person the agent acts for.
    • Return input validation problems as tool errors the model can read and correct, and keep a person in the loop for any write tool.
    Freshness and cost
    • Re-index on merge and on permission change, not on a nightly schedule.
    • Generate chunk context once at indexing time. Prompt caching lowers that cost.1
    • Cache hot reads at the gateway, keyed by identity-scoped filters so caches never leak across callers.
    Security, access and integrity
    A second brain concentrates guidance that agents will act on and that people will assume is true. It is both a data-protection target and an integrity target.
    Threat
    How it shows up
    Control
    Over-sharing amplified by search
    An agent surfaces a note nobody realised was widely readable
    Run access reviews on sources before ingestion. Default new notes to the narrowest audience.
    Stale or wrong permissions
    Someone loses access but still retrieves the note
    Filter on entitlements inside the query. Where sources support it, verify access against the authoritative source at query time and fail closed.8,9
    Cross-domain leakage
    A query in one domain returns another's restricted material
    Separate stores and indexes for restricted vaults. Enforce per-tenant isolation server-side, not in the prompt.7
    Embedding leakage
    Vectors reveal the text they encode
    Classify embeddings like their source, encrypt them, and lock down vector store access. OWASP lists these weaknesses in its 2025 LLM Top 10, and the entry carries a new number in the 2026 edition.7
    Indirect prompt injection
    A note or ingested source contains instructions aimed at the model
    Treat retrieved text as untrusted data. Sanitise and delimit it before it enters a prompt.7 Scan ingested external content. Never retrieve unapproved notes for higher-tier agents.
    Poisoning through the write path
    An agent or contributor publishes misleading guidance
    Agents propose, people approve. Branch protection, signed commits, owner review, and anomaly alerts on unusual edits.
    Secrets and personal data in notes
    Credentials or personal details get copied into a vault
    Secret and personal-data scanning in CI and at ingestion. Reject, redact or quarantine.
    History rewriting
    Evidence of what the guidance said at the time disappears
    Append-only history, signed commits, and retention rules. Supersede instead of delete.
    Instructions treated as authority
    A note says to run an action and the agent obeys
    The harness decides what is allowed, through the policy engine. Notes inform, they do not authorise.
    Two further points. Identity mapping and permission sync are security-critical infrastructure and should be owned and tested as such. And every step in the harness trace should record the note IDs and versions it relied on, because that is the evidence that guidance was approved at the moment of action.
    Quality, lifecycle and measurement
    Lifecycle
    Notes move through draft, in review, approved, deprecated and archived. Approved notes have a review due date. Past it, a note is flagged, then demoted in ranking, then excluded from retrieval by higher-tier agents until reviewed. Deprecation keeps the note, marks it, and links to its successor.
    What to measure
    Evaluate retrieval and generation separately so you know which stage to fix. Retrieval is measured with hit rate, recall at k, mean reciprocal rank and context precision. Generation is measured with faithfulness to the retrieved context and answer relevance.15 Build a golden set of questions with known source notes, include questions that should return nothing and questions the caller must be denied, and add every wrong-answer report to it. Run it on every change to the index, chunking, embeddings, reranker or model, and sample live answers with a model judge.

    Set targets from your own baseline in the pilot, then ratchet them. The same evals belong in the harness's eval suite, so a change to the second brain is tested like a change to the agent.

    Controls by UARS tier
    The second brain is a source of context, so the tier of the agent reading it decides how strict retrieval must be. This mapping is illustrative and reads each tier as adding to the one before, in line with the rest of this page.
    Tier
    Second brain controls expected
    Why
    Tier 1 Standard
    Approved-status filter. Owner and review date on every note. Entitlement filter from the caller's identity. Retrieved text delimited in prompts. Golden-set evals in the release pipeline.
    Baseline hygiene that keeps answers grounded and access correct.
    Tier 2 Agentic
    Only approved, in-date notes retrievable. Entitlements enforced inside the query. Provenance labels carried into the context. Note IDs and versions logged per step. Agents propose but never publish. Scanning of ingested external content.
    Agents act on what they read, so integrity and traceability matter, and these support the context integrity gap.
    Tier 3 Full stack
    Consequential actions draw only on enterprise-core or dual-reviewed notes. Signed, append-only history. Real-time entitlement checks against authoritative sources for sensitive content. Retrieval evals gate releases. Poisoning and injection red-team tests. Knowledge sources included in the AI inventory. Retrieval traces feed the safety case.
    High autonomy or consequence needs evidence that guidance was approved and current at the moment of action.
    For organisations in Singapore, IMDA's Model AI Governance Framework for Agentic AI, first launched in January 2026 and updated to version 1.5 in May 2026, is a complementary lens. It organises guidance into four dimensions: assessing and bounding risks upfront, meaningful human accountability, technical controls and processes, and end-user responsibility.12,16 The second brain supports each. Tiering bounds the risk, owners and approvers provide accountability, permission-aware retrieval and logging are technical controls, and cited sources let end users see where an answer came from. The framework is voluntary guidance, not regulation.

    Starter kit
    A schema file is the cheapest control you can add. It gives people and any model that helps maintain the vault the same rules, which is the role the schema layer plays in the LLM Wiki pattern.3
    Illustrative schema file excerpt
    # Knowledge schema (excerpt)
1. Raw sources are immutable. Never edit anything under /raw.
2. Every note has the required header fields. A missing owner
   or review_due fails the build.
3. One idea per note. Link glossary terms with [[term]].
4. Every claim cites a raw source or another approved note.
5. Agents create or update drafts only. A named owner approves.
6. Flag contradictions inside the note. Never resolve them silently.
7. Never copy secrets or personal data into notes.
8. A superseded note is kept, marked, and linked to its successor.
    • CI checks to switch on first: required header fields, valid status values, review date in the future for approved notes, link and ID integrity, no orphans, secret scanning, personal-data scanning.
    • A first golden set: thirty questions across the pilot domain, including five that have no answer and five the test caller must be denied.
    • A first dashboard: notes past review, owner coverage, zero-result searches, flags raised, retrieval hit rate, faithfulness.
    • A first runbook: how a note is proposed, reviewed, approved, superseded and retired.

    Terms used on this page
    
      
    Plain-language definitions, in the order a reader is likely to meet them.
    
    
    
    
    UARS
    Universal AI Use-Case Risk Score. SafeAI.sg's proposed illustrative method for scoring how risky an AI use case is, on five dimensions, and placing it in one of three governance tiers.
    AI agent
    Software in which an AI model plans and takes steps, using tools, to complete a task. A chatbot only answers. An agent acts.
    Agentic harness
    The runtime around the model. It runs the loop, assembles context, calls tools, applies checks, pauses for people and records what happened.
    Intent Window Principle
    SafeAI.sg's principle that for consequential agentic AI, governance must act before the action is taken, in the window between the agent proposing a step and the step running.
    Human-in-the-loop (HITL)
    A person reviews and approves an action before it goes ahead.
    Guardrails
    Checks on what goes into and comes out of an AI model, such as screening for injected instructions or filtering personal data.
    Prompt injection
    Hidden instructions placed in content, such as a document or web page, that try to hijack what the model does.
    Tool scope enforcement
    Limiting each agent to the tools, and the parameters of those tools, that its task needs.
    Trajectory monitoring
    Watching the sequence of steps an agent takes while it runs, so loops, drift and unusual behaviour can be caught mid-run.
    Circuit breaker
    An automatic stop that trips when a limit is crossed, such as too many steps, too much spend or too many errors.
    Generative AI firewall
    A filter at the boundary that inspects prompts and responses and blocks harmful ones.
    AI-SPM
    AI security posture management: keeping an inventory of models, agents, tools and data connections, and checking their security configuration.
    Safety case
    A structured argument, backed by evidence, that a system is acceptably safe for its intended use.
    Policy as code
    Governance rules written in a form software can evaluate, so they are applied the same way every time and can be versioned and tested.
    MCP
    Model Context Protocol, an open standard for connecting AI agents to tools and data.
    Semantic layer
    Governed definitions of business terms and metrics, mapped to real data, so every agent gets the same answer to the same question.
    Ontology
    A shared model of what exists in the business and how things relate, such as customers, policies and claims.
    Org second brain
    Human-written organisational knowledge, such as playbooks and decisions, linked together so people and agents can both use it.
    Denial-of-wallet
    An attack or accident that runs up AI costs, through excessive model calls, until the budget is gone.
    AISVS
    OWASP's AI Security Verification Standard: a catalogue of testable security requirements for AI systems, with three verification levels.
    OWASP Top 10 for Agentic Applications
    A ranked list of the ten highest-impact risks for AI agents, numbered ASI01 to ASI10, used here as a source of attack scenarios.
    Agent Control Standard (ACS)
    An OWASP specification for runtime agent control: a guardian agent permits, denies or modifies an agent's action before it happens, with traces and an agent bill of materials.
    Guardian agent
    In ACS, a separate component that inspects an agent's intended actions and returns a verdict. It plays the role of the policy engine.
    Agent bill of materials (AgBOM)
    A current list of what an agent is built from, such as models, tools and services, expressed in formats like CycloneDX.
    Evidence pack
    A signed, expiring record of test results bound to the exact versions of an agent and its components. It is the artefact a release gate checks.
    Admission control
    A check by the platform that refuses to deploy or run an agent unless it holds a valid, matching evidence pack.
    Restricted mode
    A reduced state an agent drops into when a check fails: read-only tools, a lower budget and human approval for every action.
    Error budget
    The amount of failure a release is allowed to show in production before it is rolled back.
    Canary
    A small, controlled slice of traffic, or a synthetic test, used to check that a release or a control still works.
    Harness engineering
    Building and running the software environment around a model: context, memory, tools, permissions, feedback and recovery.
    Paved road (golden path)
    The supported, easiest route for building and running an agent on the platform, with safe defaults and self-service onboarding.
    Stream-aligned team
    A team that owns a flow of valuable work end to end. Here, a use case team or outcome cell.
    Platform team
    A team that provides an internal product, such as the harness, to reduce the load on the teams that build on it.
    Enabling team
    A team that coaches other teams to build a capability and then steps back, so they become more autonomous.
    Outcome cell
    A small team, often an owner plus one or two engineers working with agents, that owns a result from discovery through operation.
    X-as-a-Service
    An interaction mode in which one team consumes what another provides through a clear interface, with little collaboration needed.
    Run-time governance
    Controlling what an agent does while it acts: deciding each consequential action before it runs, watching the run, and recording evidence. It continues for as long as the agent runs.
    Build-time governance
    Controlling software through reviews, tests and approvals before it is released, on the assumption that it then behaves as approved.
    Stage-gated lifecycle (waterfall)
    A development approach where work passes through sequential stages, with formal approval at gates. Governance is concentrated at the gates.
    Intent
    A structured statement of what an agent is about to do: the action, the target, the parameters and the purpose, checked before the action runs.
    Fail closed
    When a control cannot decide or breaks, it denies or restricts instead of allowing the action.
    Idempotency
    A property that makes repeating a request safe, so a retry cannot repeat the effect, for example by paying twice.
